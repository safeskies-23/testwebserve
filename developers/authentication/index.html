Authentication

Read this for: how a person signs in, how long the session lasts, and what happens when they change their email or password.

Source files: apps/accounts/views.py, apps/accounts/forms.py, apps/accounts/urls.py, apps/accounts/admin.py, apps/accounts/services/mail.py, apps/accounts/axes.py, config/settings.py, templates/registration/, apps/accounts/templates/accounts/settings.html, apps/accounts/templates/accounts/privacy.html

Sign-in is email and password. The stored email is lowercase, and the sign-in form lowercases the address before it checks the password. A wrong password and an unknown email show the same error. Templates for sign-in and password reset live in templates/registration/. Settings live in accounts/settings.html.

LoginRequiredMiddleware sits after the authentication middleware. A view is private unless it is marked with login_not_required. Sign-in, sign-out, password reset, registration, and the privacy page are marked. Everything else, including a view added later, redirects to sign-in. Admin views set their own login URL, so a signed-out request for /admin/ goes to the admin sign-in page.

Sign-in lands on /, which redirects to today's day page. That page is on HTMX and templates.

Session​

A normal session lasts 14 days from the last visit. SESSION_SAVE_EVERY_REQUEST refreshes that clock on each response. The cookie is HttpOnly and SameSite=Lax. Production also marks it Secure.

The sign-in form has This is a shared device. When it is checked, the view calls session.set_expiry(0). The cookie then has no expiry date, so the session ends when the browser closes. That session does not keep a browser draft. Drafts are on Entries and autosave.

Sign-out is a POST. GET is not allowed.

Password reset​

The reset form always redirects to the same done page, whether or not an account uses that email. Mail is sent only when an active account with a usable password exists. The done page does not repeat the address.

PASSWORD_RESET_TIMEOUT is one hour. The link is Django's password-reset token. It stops working once the password changes, including when the same link is opened again, and it stops working after the hour. Setting the password sends a notice to the account email and signs out other sessions on their next request.

Settings and notices​

The settings page edits the signed-in person only: name, time zone, email, and password. There is no appearance control. The time zone must be an IANA name.

Changing the email or the password requires the current password. A name or time zone change does not. A rejected save writes nothing and sends no mail.

A password change updates the hash stored in the current session, so this browser stays signed in. Other sessions fail that check on their next request and are discarded. An email change does not end sessions. The password notice goes to the account's current email. The email notice goes to the old address and does not include the new address. Neither notice includes a password.

The same notices are sent when a staff member changes the email or password in Django admin, and when a reset link sets the password.

Throttling​

django-axes locks sign-in after 5 failures for the same email and IP together. One person's misses do not lock everyone on that network. A successful sign-in clears the counter. The lock lasts one hour. The response is HTTP 429 and registration/lockout.html, which does not include the email. Axes failure logs mask the email, the password, and the IP.

apps/accounts/axes.py lowercases the posted email so Ada@Example.com and ada@example.com share one counter. The test client method login() does not pass a request, which this backend requires. Tests post the sign-in form or call force_login.

Registration and admin​

/accounts/register/ returns 404, including on POST, unless SiteSettings.allow_registration is on. The switch defaults to off. Staff change it on the site settings row in Django admin. When it is on, the sign-in page shows Register now, the page creates the account, and it signs the person in. Creating an account also creates that person's personal diary. The same is true of the admin add form and createsuperuser. How that diary is made is on Models. An invitation can create an account while this switch is off. That path is on Permissions.

Staff create accounts in Django admin. The user list has a Send set-password email action. It sends the same reset message. Inactive accounts and accounts with an unusable password are skipped. The add form still requires a password; the action is how the person receives a link to replace it.

Privacy​

/accounts/privacy/ is public. It says who can read an entry, that this is not end-to-end encryption, and which risks remain. Backup retention and account deletion are still the phrase “to be published before launch.” The same words are in docs/help/privacy.md and accounts/privacy.html. Change them together. The footer and Settings link to the app page. The page stores nothing and writes nothing to a log.
