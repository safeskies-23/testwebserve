Models

Diary and membership​

Diary stores a name, shared, in_custody, and created_at / updated_at. It does not store an owner. The owner is the membership row whose role is Owner. shared is set when the diary is created and does not change when people join or leave. A personal diary and a diary created with the box unchecked are private. Invitations are only for a shared diary. in_custody is set when the owner closes an account and leaves a shared diary that still has other members with the site administrator. After the account is erased, that diary can have no Owner row. The flag is the custodian until staff reassign or delete it.

DiaryMembership is one row per person per diary (diary_membership_one_per_user). role is Owner, Editor, or Contributor (diary_membership_role_known). is_default marks that diary as one of that person's default destinations for a new entry. Several of one person's memberships may be default, and none may be.

diary_one_owner is a partial unique constraint: at most one Owner row per diary. Creating a diary inserts that row. Admin cannot change memberships. An accepted ownership transfer demotes the current Owner to Editor and then sets the recipient to Owner in the same transaction, so the constraint is never asked to hold two Owner rows.

Who may read or change a diary or an entry is on Permissions. How a save works is on Entries and autosave.

Personal diary​

User.save runs inside a transaction. A post_save receiver then creates one diary and one Owner membership with is_default set. The diary is named from the display name, as in Ada's Personal Diary. Registration, Django admin, createsuperuser, and User.objects.create_user all save a new user, so each of them gets that diary. A later save of the account does not add a diary or rename the one that exists.

A diary created on the Diaries page is owned by that person and is not a default until they check it. Checking Shared diary sets shared. Leaving it unchecked creates a private diary.

Deleting a user deletes their memberships. A diary with no memberships left is deleted with them, unless in_custody is set. Account erasure uses that path for a shared diary that still has other members: the diary stays, the Owner row is removed, and staff reassign it from the custody screen. A direct User.delete() still cannot drop an entry, because owner and original_submitter use PROTECT until the deletion service clears them.

The migration backfills one personal diary for each account that already existed.

Entry​

Entry stores the current owner, the original submitter, author_name, the raw text, the calendar date the entry is about, the timezone-aware time it was submitted, and a revision that starts at 1. original_submitter is set when the entry is created and does not change when the entry is transferred. The owner link and the original-submitter link are nullable and PROTECT. author_name is empty until the owner closes the account, which copies the display name onto each entry they own. While that person can sign in, a shared entry shows the live display name. After they cannot, it shows author_name. entry_raw_text_not_blank rejects blank or whitespace-only text. entry_revision_at_least_one rejects a revision below 1. autosave_editor and autosave_write remember the last autosave from one open editor so an older write from that editor cannot replace a newer one. They are not diary text. processing_instructions is an empty text column. Nothing reads or writes it.

A direct delete of an account that still owns an entry, or that is recorded as an original submitter, fails, so the delete cannot drop the text. An invitation's inviter, a transfer's sender, and an audit row's actor are PROTECT for the same reason. The deletion service clears those links first, then deletes the user. How that runs is on Authentication.

EntryMembership ties one entry to one diary (entry_membership_one_per_diary). The same entry can belong to more than one diary. Deleting the entry deletes those rows.

Invitation and audit​

Invitation is one pending row per diary and email (one_pending_invitation). It stores the inviter, the email, the offered role (Editor or Contributor), a single-use token, expires_at, and state (pending, accepted, declined, or revoked). Sending again to the same email updates that pending row, including a new token, so the previous link stops working. A pending row whose time has passed is treated as unusable and is replaced by the next send. The token is the only copy that opens the link. The row does not store diary text.

OwnershipTransfer is one pending row per diary (one_pending_ownership_transfer). EntryTransfer is one pending row per entry (one_pending_entry_transfer). Each stores the sender, the recipient email, a token, and state (pending, accepted, declined, or cancelled). There is no expiry. The rows do not store diary text. Deleting an entry deletes its transfer rows. The audit row keeps the entry id.

AuditEvent stores the actor (null when someone declines before they have an account, and null after that account is erased), the action, the diary, affected_user_id, and affected_entry_id. The diary link is cleared, not deleted, when the diary itself is deleted, so a custody delete still has a row. Invitation actions are invitation_sent, invitation_accepted, invitation_declined, and invitation_revoked. Membership actions are role_changed, member_removed, and member_left. Entry actions are entry_removed, entry_deleted, and entry_moved. Transfer actions are ownership_offered, ownership_accepted, ownership_declined, ownership_cancelled, entry_transfer_offered, entry_transfer_accepted, entry_transfer_declined, and entry_transfer_cancelled. Custody and account actions are custody_opened, custody_retained, custody_reassigned, custody_deleted, custody_returned, account_deactivated, and account_erased. A role change does not record the previous role. The affected entry id is null except for an entry action or an entry transfer, and it remains after the entry row is gone. The row does not store diary text, an email, or a token. Permanent deletion clears affected_user_id when it pointed at the erased account.

User.deactivated_at is empty until the person deletes the account. SiteSettings.deletion_grace_days defaults to 90. The name shown on a shared entry is the account's current display name until that account is closed, and then author_name.

Not on these tables​

processing_instructions is stored and unused.
