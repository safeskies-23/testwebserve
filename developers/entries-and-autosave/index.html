Entries and autosave

Read this for: creating and editing an entry, autosave, the browser draft, and the revision check.

Source files: apps/diary/services/entries.py, apps/diary/views.py, apps/diary/forms.py, apps/diary/templates/diary/entry_form.html, apps/diary/static/diary/autosave.js, templates/base.html

Fields are on Models. Who may read, edit, or delete is on Permissions.

Save​

create_entry stores one row and one membership per chosen diary. The text must contain a non-whitespace character, or nothing is stored. The request must name at least one diary the person may add to. A diary they cannot read returns 404. A diary they can read but may not add to returns 403. An omitted date is today in that person's timezone. The submitted time is timezone-aware and later edits do not change it.

update_entry is only for the current owner. It stores the new text and the posted diary list, and it stores a posted date when one was sent. A blank date leaves the referenced date as it is. The text is stored as submitted, including surrounding spaces. Diaries the person cannot read stay on the entry. Changing the diary list does not change the current owner. When a shared diary is added or removed, that writes an entry_moved audit row and does not store the text. A change that only involves private diaries writes no row. The revision has to match the saved row. The save then increments it by one. Text, date, and diaries all wait on that check, so a stale form cannot change any of them.

A mismatched or missing revision raises RevisionConflict before any write. The form is shown again with the submitted text, date, and diaries, and a link to reload the saved entry. An autosave response is JSON {"state": "conflict"} with status 409 and does not include the text.

The service does not log the text. processing_instructions is not read or written. It stays empty.

Autosave​

The editor loads diary/autosave.js. There is no build step and no inline script. The script waits until typing has paused for one second, then sends the text, date, diaries, revision, an editor id, and a client write number. It keeps one request in flight. A response is applied only when its write number is the newest one this page sent. Blank or whitespace-only text is not sent. The server still rejects it and creates nothing.

The first confirmed save creates the entry. There is no server draft row. The browser then replaces the address with /entries/<id>/, the heading becomes Edit entry, the date hint changes to keeping the saved day, and later saves go to /entries/<id>/autosave/. POST /entries/autosave/ is the create. GET on either address returns 405. A repeated create with the same editor id and write number returns the entry already stored and does not insert another. A repeated update with that same pair returns the stored row and does not change it. A lower write number from the same editor changes nothing, even if it sends the current revision. A different editor is judged only by the revision, so another tab or device is a conflict rather than a silent overwrite.

The page shows one of these states, in text and in color: Saving, Saved, Offline (will retry), Conflict, and Error. Offline retries when the browser is back online. Conflict leaves the typed text in the box and offers Load the saved entry and Copy your text. Error is a validation failure, such as no diary or blank text, and the response message does not include the entry text.

While the page differs from the last confirmed save, closing or leaving it asks the browser to confirm.

A normal session also writes a browser draft to IndexedDB as the person types. The record is keyed by that person and the entry (or new). It expires after 14 days, which is the same length as a normal session. A confirmed save deletes it. Opening the editor offers to restore a draft whose text, date, or diaries differ from the form. This is a shared device renders data-drafts="off", and that session does not write a draft. Signing out loads the sign-in page with data-clear-drafts, and the script deletes this browser's draft database. The draft is plaintext any script on this origin can read. It is not a saved entry, and it is not in the database.

Pages​

/entries/new/ and /entries/<id>/ use diary/entry_form.html. The diary boxes on a new entry start from that person's defaults. ?date=YYYY-MM-DD fills the date. Anything else leaves it blank. The same form edits an entry the person owns. Someone who can read it but does not own it sees the text and, when allowed, a Remove from button for each diary they may delete from. They do not get the editor. The current owner sees Delete entry, which removes it from every diary. Either redirect goes to that entry's day. Who may delete is on Permissions.

Save entry still posts the form when the script does not run. With the script, that button saves immediately through the same autosave path. Reading a day is on HTMX and templates.
